# 통합 후 문제 분석 및 수정 보고서

작성일: 2026-10-18 (한국 시간)  
대상: 현재 `TCP_Clean_Management` 작업 트리, seokhyeon09/main `2960e8199747cb27dfad0e0a4f462986be3935fc` 통합 이후

## 결과와 범위

시설 등록·수정, 장치 이동과 MAC 교체, 센서 현재값·이력 조회, 장치 키, 청소·체크리스트, 시설 메타데이터의 실제 결함을 분석하고 아래 12개 항목을 수정했다. 일부는 직전 통합 과정에서 생긴 회귀이며, 기존 코드에 있던 오류도 함께 포함한다.

운영 DB, 외부 Upstash, 실물 ESP32를 변경하지 않았다. 이번 수정 전 파일 182개와 diff는 `.git/codex-backups/post-sync-fixes-20261018-031759/`에 보관했다. 기존 작업과 이전 통합 내역을 유지했으며 커밋·푸시·배포는 수행하지 않았다.

이 보고서는 수정한 경로와 재현 사례에 대한 검증 기록이다. 모든 외부 서비스·하드웨어·운영 환경에 문제가 없다는 보증은 아니다.

장치 이동 이전의 대기 패킷은 잘못된 구역에 자동 기록하지 않는다. 거부된 패킷은 ESP32의 기존 큐 정책에 남으므로, 과거 장소 데이터 복원이 필요하면 별도의 확인된 복구 절차가 필요하다. 장치 측정 시각의 초 단위 한계까지 없애는 펌웨어 프로토콜 변경은 이번 범위에 포함하지 않았다.

## DB 적용과 보존

새 마이그레이션은 `backend/src/main/resources/db/migration/V4__facility_metadata.sql`이다.

- `zones.floor VARCHAR(8) NULL`, `zones.gender VARCHAR(8) NULL`을 추가한다.
- 기존 행의 층수·성별은 NULL로 유지한다. 임의 값을 추정해 채우거나 기존 행을 삭제하지 않는다.
- V1~V3 SQL은 수정 전 백업과 바이트 단위로 동일하다. 기존 체크섬을 바꾸지 않았다.
- V3까지 적용된 DB는 업데이트된 백엔드 시작 시 Flyway가 V4를 적용한다. 운영 적용 전 기존 [DB 백업·이전 절차](security-upgrade.md#flyway-이전복구)를 따른다.
- 운영 DB를 이번 작업에서 접속·마이그레이션하지 않았다. 기존에 이미 잘못 저장된 주소·좌표는 실제 위치를 알 수 없어 일괄 교정하지 않았다.
- 실제 AI 모델·런타임 파일 17개, AuthService와 AuthContext도 수정 전 백업과 동일하다. 기존 서버 세션·BCrypt·장치별 키·실제 모델 추론 경로를 유지했다.

## 검증 결과

| 검증 | 최종 결과 |
|---|---|
| Java 17 전체 백엔드 회귀 테스트 (MySQL 전용 테스트는 아래 별도 실행) | 123개 성공, 실패·skip 0 |
| 실제 MySQL 8.4.10 | 28개 성공, 실패·skip 0: 마이그레이션 6개 + 시설·인증·센서·이동 등 통합 시나리오 22개 |
| 실제 동봉 모델을 로드한 Python 테스트 | 8개 성공 |
| 프론트엔드 Node 테스트 | 48개 성공, 실패·skip 0 |
| Vite 8.3.1 배포용 빌드 | 성공, JS 733.39 kB / gzip 210.69 kB |
| oxlint: src, test, vite.config.js | 오류 0, 경고 30 |
| git diff --check | 통과 |

MySQL 통합 시나리오는 백엔드 테스트 중 일부를 MySQL 데이터소스로 다시 실행한 결과다. 위 개수를 서로 다른 전체 테스트 개수로 합산하지 않는다.

검증은 외부 네트워크를 차단한 일회용 컨테이너에서 수행했다. 프로젝트 및 도구는 읽기 전용으로 제공하고 쓰기는 용량 제한 tmpfs에 한정했다. 실제 환경 변수·인증 키·운영 DB를 마운트하지 않았으며, MySQL도 호스트 포트를 노출하지 않은 격리된 루프백만 사용했다. Java는 기존 런타임 및 테스트 jar를 이용해 전체 소스·테스트를 컴파일하고 JUnit Platform으로 실행했다. 호스트 의존성이나 프로젝트 lockfile은 변경하지 않았다.

표준 회귀 명령은 다음과 같다. 해당 환경에 Java 17, 프로젝트 의존성 및 backend/ai/requirements.txt의 Python 의존성이 필요하다.

```sh
cd backend
./gradlew test
ai/.venv/bin/python -m unittest discover -s ai/tests -v
cd ../frontend
npm test
npm run build
npm run lint
```

`MySqlMigrationTest`는 `TCP_MYSQL_TEST_URL`, `TCP_MYSQL_TEST_USER`, `TCP_MYSQL_TEST_PASSWORD`를 지정한 **검증 전용 서버**에서만 실행한다. 테스트가 생성한 임시 DB를 제거하므로 운영 서버 자격증명을 사용하지 않는다.

## 남아 있는 확인 사항

- 프론트엔드 JS가 500 kB를 넘는 번들 크기 경고와 lint 경고 30개가 남는다. 빌드 및 lint 오류는 없다.
- 실제 카카오 지도 검색·휴대폰 GPS 권한·외부 Upstash 응답·실물 ESP32 통신·운영 서버 배포는 이번 검증 범위 밖이다. 펌웨어는 이번에 변경하지 않았다.
- 이전 통합에서 자동 승인 검토가 거절한 보관기간 변경 및 Upstash 패킷 자동 삭제 확대는 추가하지 않았다. 기존 원본 데이터 7일 정리 정책을 유지한다. 관련 범위는 [직전 통합 내역](seokhyeon-sync.md#승인-대기-항목)에 기록돼 있다.
