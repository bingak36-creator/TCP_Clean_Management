# 보안·운영 일관성 변경 및 배포 절차

2026-10-17 잔여 문제 목록 중 1, 2, 4, 6, 7, 8, 9, 12~21, 24, 25, 26번을 반영했습니다. 기존 AI 모델과 측정 이력은 유지합니다. 3번의 청소 기록 입력 필드 제한은 담당 구역 권한 우회를 막는 데 필요한 범위에서 함께 적용했습니다.

## 역할과 담당 구역

| 기능 | DEVELOPER | ADMIN | CLEANER |
|---|---|---|---|
| 공개 구역 요약 | 공개 | 공개 | 공개 |
| 장치 목록·이력, 알림·AI 결과, 청소 기록 조회 | 전체 | 배정 구역 | 배정 구역 |
| 체크리스트·청소 기록 작성 | 전체 | 배정 구역 | 배정 구역 |
| 알림 조치·출동·구역 활성화·구역 가스 임계값 | 전체 | 배정 구역 | 불가 |
| 시설·센서·작업자 등록/삭제, 장치 수정·키 발급, 계정·권한 관리 | 허용 | 불가 | 불가 |
| 공통 운영 설정 변경 | 허용 | 불가 | 불가 |

미배정 ADMIN/CLEANER는 관리 대상이 없습니다. 프런트 화면의 숨김 여부와 관계없이 서버가 권한을 검사합니다. 권한·역할 변경은 다음 API 요청부터 적용됩니다. 화면의 배정 목록은 새로고침하면 갱신됩니다.

개발자가 사용하는 계정 API:

- `GET /api/admin/users`: 비밀번호를 제외한 계정·역할·배정 목록
- `POST /api/admin/users`: `{username,password,role,zoneIds}`로 명시적인 계정 생성. 비밀번호 최소 12자·최대 UTF-8 72바이트
- `PUT /api/admin/users/{id}/access`: `{role,zoneIds}`로 역할과 배정 변경. 본인의 개발자 권한 제거는 차단

기존 DB에 개발자 계정이 없다면 DB 관리자가 승인한 기존 계정 하나에만 명시적으로 DEVELOPER 역할을 부여하고 배정을 진행해야 합니다. 자동 승격·공개 가입은 없습니다. 이전 자동 가입으로 생성된 계정은 별도로 검토해야 합니다.

조치·설정·체크리스트의 작성자 ID는 인증된 사용자에서 정합니다. 청소 기록의 `createdBy`도 서버가 기록합니다. 요청 본문의 `id`로 기존 청소 기록을 수정할 수 없습니다. 알림 일괄 조치는 배정 구역에만 적용됩니다. 규칙 알림의 자동 정상 복귀에는 `resolutionSource=RECOVERY`, 수동 조치에는 MANUAL을 기록합니다.

## 장치별 키 전환

공유 환경 변수 `IOT_DIRECT_API_KEY`는 더 이상 인증에 사용하지 않습니다. 각 MAC에 키를 따로 발급해야 합니다.

1. 개발자 계정으로 실제 장치의 Device Set을 등록하거나 기존 Upstash 장치를 확인합니다.
2. 시스템 설정의 기기 목록에서 해당 MAC의 인증 키를 발급합니다. `POST /api/admin/device-credentials/{mac}/rotate`도 사용할 수 있습니다.
3. 반환된 키는 한 번만 표시합니다. 서버 DB에는 SHA-256 해시만 저장합니다. 프런트 일반 설정·로컬 저장소에는 키를 저장하지 않습니다.
4. 해당 ESP32 설정 포털에 키를 저장합니다. 펌웨어는 `X-Device-Key`, `X-Device-Mac`을 함께 보냅니다. 본문의 MAC과 대상 센서도 인증된 MAC에 속해야 합니다.
5. 키 재발급은 이전 키를 즉시 무효화합니다. `DELETE /api/admin/device-credentials/{mac}`로 개별 폐기합니다. MAC 교체와 Device Set 삭제 시 이전 MAC의 키도 비활성화합니다.

`GET /api/iot/devices`, 장치 이력, Upstash 상태는 관리자 세션이 필요합니다. 일반 사용자는 `/api/public/zones`와 구역 상태 요약을 조회합니다. 공개 이름에 들어 있던 MAC 문자열도 가립니다.

## 설정·상태·실패 처리

- 공통 임계값은 `temp_warning_threshold`, `temp_danger_threshold`, `humidity_warning_threshold`, `humidity_danger_threshold`, `gas_warning_threshold`, `gas_danger_threshold`입니다. 온도 -40~80℃, 습도 0~100%, ADC 0~4095이며 주의 값은 위험 값보다 낮아야 합니다.
- `offline_timeout_seconds`는 15~86400초, `polling_interval_seconds`는 5~300초, `clean_warning_interval_hours`는 1~168시간입니다. `alert_cooldown_seconds`는 30~86400초입니다. 소수인 시간 설정과 알 수 없는 키는 거부합니다.
- 온습도 기준은 전체 공통, 구역별 가스 기준은 Zone에 저장합니다. 임계값 일괄 저장과 출동 지시는 한 트랜잭션으로 처리합니다. 실패하면 일부 성공을 전체 성공으로 표시하지 않습니다.
- 설정은 저장 성공 후 적용합니다. 다른 관리자가 변경한 폴링 주기는 다음 갱신에서 반영합니다. 원본 보관 정책은 현재 7일이며 조작 가능한 가짜 보관 기간 입력은 제거했습니다.
- 상태 API는 NORMAL/WARN/DANGER/UNKNOWN/NO_DATA/STALE/INACTIVE를 실제 측정에서 결정합니다. 데이터 부족·통신 중단·운영 중지를 정상으로 바꾸지 않습니다. 비활성 구역은 공개 목록에서 빠지고 새 센서 입력이 HTTP 409로 거부됩니다. 관리 목록에는 남아 재활성화할 수 있습니다.
- 센서별 전송·직접 전송·Upstash 수집 모두 정규화된 측정 행을 조회합니다. MAC·수집 출처를 측정 행에 보관하며 측정 이력은 MAC과 패킷 키 단위로 묶습니다. MQ-7 선택 값도 별도 측정으로 보존합니다. 이력 조회의 기존 1,000패킷 제한은 유지합니다.
- 측정 시각은 UTC로 저장하며 미래 5분을 초과하거나 1970년 이전인 시각은 거부합니다. 체크리스트는 서울 날짜를 사용하고 잘못된 날짜를 오늘 날짜로 바꾸지 않습니다. 체크 저장에는 `isCompleted`가 필수이며, 동시에 같은 항목을 저장해도 중복 행을 만들지 않습니다.
- 청소 완료는 기록과 청소 메타데이터만 바꿉니다. 가스·온습도·위험 상태를 임의로 변경하지 않습니다. 저장·조회 실패는 오류로 표시하고 성공 메시지를 내지 않습니다.
- 규칙 기반 알림은 센서·유형·설치·판정 출처별로 진행 중인 건을 재사용합니다. 정상 복귀와 재알림 간격을 처리하며 비활성 구역·오래된 측정은 새 경보를 만들지 않습니다. AI 입력은 모델 준비용으로 유지하되 오래된 측정으로 새 실시간 경보를 발행하지 않습니다.

요청 제한 기본값은 로그인 IP당 10회/분, 아이디당 10회/15분, 장치 수신 IP·MAC 각각 120회/분입니다. `app.traffic.login-limit`, `account-limit`, `device-limit`으로 설정합니다. Redis 카운터 증분과 만료 설정은 Lua로 원자적으로 처리하며 Redis 장애 시 인증·수신을 무제한으로 열지 않습니다. 메모리 모드는 한 프로세스 개발용입니다.

## 운영 비밀번호와 HTTPS

루트 `.env.example`을 Git에서 제외되는 `.env`로 복사하고 권한을 600으로 제한한 뒤 서로 다른 긴 무작위 비밀번호를 설정합니다. 기본 비밀번호는 없습니다. Compose는 필수 값이 비어 있으면 실행을 거부합니다.

- `MYSQL_ROOT_PASSWORD`, `MYSQL_PASSWORD`, `REDIS_PASSWORD`
- `TLS_CERT_DIR`: 실제 서비스 도메인에 유효한 `fullchain.pem`, `privkey.pem`이 있는 디렉터리. 인증서는 읽기 전용으로 마운트하며 비밀 키는 접근 권한을 제한합니다.
- 필요할 때만 `TCP_BOOTSTRAP_USERNAME`, `TCP_BOOTSTRAP_PASSWORD`. 빈 사용자 DB에서만 최초 개발자를 생성하므로 기존 계정을 덮어쓰지 않습니다.

**이미 존재하는 MySQL 볼륨에서는 환경 변수 변경만으로 비밀번호가 바뀌지 않습니다.** DB 관리자가 기존 root·애플리케이션 계정의 비밀번호를 먼저 변경하고 새 `.env` 값과 맞춘 뒤 재시작해야 합니다. 이 작업은 운영 DB에서 자동 수행하지 않습니다.

MySQL·Redis·백엔드 포트는 호스트에 공개하지 않습니다. DB와 Redis는 내부 네트워크에 두고 외부에는 Nginx 80/443만 노출합니다. 80은 HTTPS로 리디렉션하며 TLS 1.2/1.3, HSTS, 16KiB 요청 크기 제한을 적용합니다. Nginx가 클라이언트 IP 헤더를 직접 설정합니다. 다른 프록시를 추가한다면 신뢰할 프록시 범위도 함께 검토해야 합니다.

Docker 외 로컬 Gradle 실행은 `.env`를 자동으로 읽지 않으므로 Spring 환경 변수를 export해야 합니다. 기본 서버 바인딩은 127.0.0.1입니다. Vite 개발 프록시는 로컬 개발용입니다. 공개 배포에는 유효한 서버 인증서를 사용하세요.

## Flyway 이전·복구

기본 `ddl-auto`는 validate이며 Flyway가 스키마를 관리합니다. 테스트의 H2 create-drop 설정은 운영과 분리됩니다.

- V1: 이번 수정 직전의 측정 항목·설치 이력·AI·세션 테이블 기준선
- V2: 역할·권한 제약, 장치별 키, 측정 MAC·수집 출처, 감사 필드, 선택적 MQ-7 연결 추가

빈 DB는 V1/V2를 자동 적용합니다. 기존 데이터를 가진 DB는 자동으로 기준선을 지정하지 않습니다.

기존 DB 이전 순서:

1. 서비스 쓰기를 중지하고 `mysqldump --single-transaction --routines --triggers --hex-blob --set-gtid-purged=OFF` 등으로 DB 전체를 백업합니다. Compose에서는 mysql 컨테이너 안에서 실행해 비공개 네트워크를 유지합니다. 비밀번호를 명령줄 인수에 넣지 말고 비공개 옵션 파일이나 대화형 입력을 사용합니다.
2. 별도 DB에 백업을 복원해 검증합니다. 더 오래된 `value1/value2` DB라면 기존 `backend/db/`의 측정 항목·설치 이력·AI·세션 이전을 먼저 끝내고 V1 구조와 비교합니다.
3. DB가 V1 구조임을 확인한 경우에만 최초 한 번 `SPRING_FLYWAY_BASELINE_ON_MIGRATE=true`, `SPRING_FLYWAY_BASELINE_VERSION=1`로 시작해 기준선을 등록하고 V2를 적용합니다. 빈 DB에는 기준선 옵션을 사용하지 않습니다.
4. 즉시 기준선 옵션을 제거하고 재시작합니다. 이후에는 체크섬 검증과 JPA validate로 누락·불일치 시 시작을 중단합니다. clean과 자동 repair는 사용하지 않습니다.
5. 새 측정 입력, 권한 제한, 기존 이력, AI 상태를 확인합니다. 실패 시 서비스를 중지하고 백업과 그 백업에 대응하는 애플리케이션 버전을 별도 복구 DB에서 함께 복원합니다. 새 컬럼을 지우는 임의의 역방향 SQL로 복구하지 않습니다.

V2는 기존 측정·계정·설치·AI 결과를 삭제하지 않습니다. MAC을 이전 설치 이력·장치 매핑에서 채우고, 중복 권한은 한 건으로 정리합니다. 인증에 쓰이지 않았던 UI 전용 `device_key` 설정만 제거합니다. 기존 자동 가입 계정의 삭제나 자동 승격은 하지 않습니다.

## 검증 명령

```sh
cd backend
./gradlew test bootJar
cd ../frontend
npm test
npm run build
npm run lint
```

실제 MySQL 검증은 운영 DB와 분리한 서버에 `TCP_MYSQL_TEST_URL=jdbc:mysql://127.0.0.1:<port>/`, `TCP_MYSQL_TEST_USER`, `TCP_MYSQL_TEST_PASSWORD`를 설정하고 `./gradlew test --tests '*MySqlMigrationTest'`로 실행합니다. 테스트는 자신이 만든 임시 DB만 삭제합니다.

HTTPS 설정은 `python3 backend/scripts/validate-deployment.py --nginx <nginx 실행 파일>`로 일회용 인증서와 로컬 포트에서 확인할 수 있습니다. 실제 공개 인증서 발급·서비스 배포·기기 업로드는 별도 운영 작업입니다.

## 이번 변경의 검증 결과

- 백엔드 106개 테스트 통과: 기존 수집·설치 이력·AI와 역할/구역 인가, 작성자 위조, 키 교체·폐기, 요청 제한, 설정 롤백, 체크리스트 20개 동시 요청, 중복 알림을 검증했습니다.
- 위 테스트 중 실제 격리 MySQL 8.4 검증 4개도 실행했습니다. 빈 DB 생성, 이전 측정·계정 보존, 실제 애플리케이션의 validate 시작, 체크섬 불일치 차단, 모르는 비어 있지 않은 DB의 자동 기준선 방지를 확인했습니다.
- 프런트 20개 테스트와 배포 빌드·린트 통과. 기존 린트 경고와 번들 크기 경고는 남아 있습니다.
- 번들된 실제 AI 모델 5개에 대한 Python 테스트 8개 통과.
- 스케치와 같은 큐 코어의 재부팅·재시도·부분 ACK·쓰기/삭제 실패·용량·손상 보존 테스트 통과. ESP32 컴파일 통과.
- 필수 비밀번호·인증서 경로 누락 시 Compose 거부를 확인했습니다. Docker 엔진은 실행되지 않아 전체 컨테이너 실행은 하지 않았습니다.
- 공식 Nginx 소스로 작업 폴더에 만든 실행 파일로 HTTPS 인증서 검증, HTTP 리디렉션, HSTS, 프록시 헤더 덮어쓰기, 큰 요청 거부를 실제 실행 확인했습니다. 시스템 전역에 설치하지 않았습니다.
- 운영 DB·공개 서버·실제 ESP32에는 적용하지 않았습니다. 기존 MySQL 비밀번호 변경, 실제 인증서 배치, 계정 배정과 장치별 키 설정, 펌웨어 업로드 및 전원 차단 시험은 배포 과정에서 수행해야 합니다.
